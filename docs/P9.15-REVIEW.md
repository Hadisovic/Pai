# P9.15 member awareness

This draft builds on [P9.14.1 #51](https://github.com/Hadisovic/Pai/pull/51) at `d9b0a30eee12560268275e49d7b75ec328d168bd`. Golden `v9.11` remains the approved personality and running TEST revision.

## Assessment and design

The existing archive already keys speakers by immutable Discord IDs and retains channel-local human messages with deletion and retention. The golden timeline pseudonymizes speakers and strips native mention markup. It could leave a mentioned member unresolved when the member lacked a recognized speaking turn. The assistant receipt layer verifies a delivered answer and its human dependencies. It does not index assistant text as facts.

Reuse Discord's Guild Member and allowed-mentions API, the existing FTS archive, and the P9.14.1 bounded request context adapter. TomoriBot's persona and memory approaches were considered in P9.14. The AGPL project has broader data and tool scopes than this extension needs. No external code, database, models, or inference providers were added. Discord's developer policy limits API data use and bars profiling. The optional local directory therefore handles only functional identity labels, explicit user controls, and narrow existing source messages. It computes no user traits or persistent rankings. [Discord Guild Member API](https://docs.discord.com/developers/resources/guild) · [Discord Message API](https://docs.discord.com/developers/resources/message#allowed-mentions-object) · [Discord Developer Policy](https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy) · [SQLite FTS5](https://www.sqlite.org/fts5.html) · [P9.14 alternatives](P9.14-REVIEW.md)

- The same guild, channel and Discord user ID identify a member across display-name and username changes. Up to four observed name pairs per member link to that member's archived messages. No backfill runs. Retained previous names, a quoted name, a typed `@alias`, or a member-chosen nickname resolve only on a unique match. Native Discord targets use the parsed mention IDs and current channel access.
- The optional request block separates the requester, explicit references, current participation and the bounded authorized roster. It selects at most four authorized members, prefers current participants in group samples, and never adds Pai to the human group by default. Discord IDs stay local. Request-scoped member markers can render as at most three distinct user mentions. On an explicit tag request, an unambiguous rendered name can also become a mention. Raw user, role, channel and mass-mention syntax is stripped from model output. Discord sends with `AllowedMentions.none()`, including native replies.
- For member-specific historical recall, search the referenced member's own eligible same-channel messages for a narrow self-stated favorite game, book or snack. Use the newest matching evidence and render a verified source link. The UTC calendar defines “yesterday.” Hearsay, guessed traits, old assistant output and broader raw conversation excerpts are outside this path. The model can express a contextual, playful comparison with limited evidence. Explicit roasts require each included member to allow teasing. Appearance and sensitive-attribute queries receive a short local boundary response.
- The member plan checks feature consent, archive sources and channel membership before generation and refreshes them before sending. Source deletion, correction or withdrawal can drop an in-flight answer. The existing social layer can supply a relevant learned group meaning independently. Ordinary assistant receipts still work when all extensions are enabled. Member-augmented replies stay out of assistant replay and receipt storage until that layer can carry the additional member-scope dependencies.

## Synthetic evidence and cost

The local rolling Qwen ledger blocked the primary-only run before any provider call. A fresh replay retained the normal Qwen-first route order and allowed the existing GPT-OSS 120B Free fallback to run. Four synthetic calls used 2,418 reported tokens. The archived private conversations were outside both runs. All four requests kept the same system instructions. We replayed the recorded outputs through the final renderer with byte-identical payload, system and prior roles, with no second inference call.

| Synthetic request | Observed answer |
| --- | --- |
| Ask about Briar's favorite game, with member context off | “tunic 🫡”. The recent messages already contained the correction. |
| Same request, with member context on | “Briar's favorite game is Tunic” with the verified source link. The feature selected Briar's correction and excluded the requester's competing preference. |
| Give two members jobs at a haunted bakery and mention both | GPT-OSS cast Rue as the night-shift “ghost-whisperer” for cursed croissants and Briar as a “spook-scented” front-of-house barista. The final replay produced two native user mention tokens. |
| Rank the group by who gets lost first in a fictional Minecraft maze and mention both | “briar would probably wander off first, then rue would catch up 🤨”. The final replay produced both validated mention tokens and kept the one-line answer. |

GPT-OSS wrote names in the group outputs instead of the requested markers. The explicit-tag renderer can recover unique names without trusting raw IDs. The mock Discord adapter verified the native markup and empty notification parse list. Actual Discord client clickability and notification behavior remain live-pilot checks. This small fallback sample cannot establish general quality or Qwen behavior.

The sourced recall used 53 more reported tokens than the matched control. Member planning makes no additional inference calls and caps its block at 780 UTF-8 bytes. A two-member local test block used 541 bytes. In one Windows sample with 32 synthetic archived messages, the optional schema and labels grew SQLite by 16 KiB. Median new and repeat name observations were 5.33 ms (four) and 1.07 ms (28). Median lookup, plan and revalidation was 8.94 ms (32). This excludes Discord reads and provider time. A member-aware turn can make up to four targeted guild member reads per permission-check phase, in addition to the existing requester checks.

## Consent, deployment and rollback

1. Keep the extension disabled until the owner approves the build and notice. The earlier Discord-review, text-memory and social-learning consents cover separate purposes. For a private TEST pilot, explicitly cover retained identity labels, alias history, self-stated cross-member recall, selected data sent to Groq, and non-notifying references. Collect new affirmative opt-in from each participant in the exact authorized scope.
2. Verify an encrypted pre-cutover archive and erasure checkpoint. With the previous process stopped and the approved checkout pinned, add `member_awareness_opt_in: true` and the separately consenting `member_awareness_member_ids` as a subset of text consent in the private policy. Reuse the existing private channel, free credentials and launch configuration. Keep media disabled. Start one instance and verify the revision and active routes.
3. Use separate consenting synthetic users to test a normal reply, incoming and outgoing multi-member mentions, member ACL revocation, a nickname change, a corrected fact, and a withdrawal. Verify client clickability and no member or reply ping. Each member can use the private `/member_context` command for their own nickname, clickable references and explicit teasing. Teasing defaults off, and clickable references can be turned off without opting out of recall. Settings expire with configured retention. Full opt-out uses `/forgetme`. Operators can remove a member from the additional opt-in while preserving still-authorized ordinary text.
4. To roll back, stop the candidate and verify that it exited. Disable member awareness in the current private policy and apply it from P9.15 while disconnected with the existing `--apply-policy` flow. This purges identity labels and controls while preserving current erasures and other authorized data. Remove the new policy keys before a build that predates them. Restore the approved golden process at its pinned revision and verify a synthetic mention. Only use the encrypted backup if needed, after applying current revocations and erasures. [Setup and existing privacy operations](SETUP.md)

No live deployment, restart, database change or merge took place. P9.12 GIF integration, P9.14.2 diagnostics and the Gateway reliability follow-up remain separate. Keep the known imminent-distress response limitation on the safety review before rollout.
